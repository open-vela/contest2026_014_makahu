## 三种事实分开保存

新增 `ROOT/visible-outgoing/<peer>/`，每个已涉及位置有独立元数据，head 保存有界核对的历史回执前缀。来源身份、位置、原文 ID、SHA 和总大小始终绑定本机不可变 journal；每次读取都重新核对实际原文，不接受对端提供的文件路径。

每个位置区分：

- 已准备随机槽 token：只说明本机准备了一个同 peer/source/sequence 绑定的标记。
- `original_offered`：应用曾按分享策略准备向此对端提供对应原文；不是载体送达或完整接收证明。
- `slot_confirmed`：对端确认保存同一 token 的保留槽，只能证明覆盖。
- `original_confirmed`：对端给出匹配原文身份、完整 SHA 和总大小的原文回执；不得由 token、槽确认、offered 或 carrier ACK 推导。

元数据中的 ID、SHA 和大小仅用于本机校验，后续槽帧不得将它们带出。token 使用既有安全熵入口生成独立 16 字节随机值，不从内容/事件 ID 派生；同一对端的位置一旦有 token 就不重新生成。其他对端的登记和 token 独立。

槽确认与完整原文确认是单调历史标记，补发、撤销共享或后来的槽确认都不会清除已有原文回执，也不触发原文、音频、业务事件或投影删除。

## 公开存储接口与授权边界

`buffer_source_events.h/.c` 增加：

- `buffer_source_visible_prepare`：持久登记随机 token。
- `buffer_source_visible_offered`：核对精确原文 SHA/大小，登记应用批准的原文提供状态并返回既有 token。
- `buffer_source_visible_accept_slot`：只接受本机已准备、同一对端/来源/序号的相同 token。
- `buffer_source_visible_accept_original`：只接受此前允许提供原文的位置，核对完整 SHA、大小与原文绑定。
- `buffer_source_visible_progress`：核对历史覆盖与原文回执前缀。

公开入口不允许调用者已持有 journal 锁；内部统一持有既有本机 journal 锁，不新增 sender→journal 反向锁序。实时授权回调只读取通道状态，不进入 Fabric 或 journal；进入、事实写入前及返回前复核授权。关闭 source journal 的构建返回 ENOTSUP，清空结果，不虚报支持。

存储方法不授予 payload 分享权限。后续网络层必须先核对当前分享策略、具体请求和 session/generation，才登记 offered 或准备原文响应，并在每片和缓存重试前再次核对。新的原文回执/证明路径也需要审查当前可见性，不能成为查询未获准原文哈希的接口。纯槽位置从未 offered 时，存储层拒绝把原文哈希请求转成完整回执。

原文回执通常带回对应 token；旧的直接原文响应若在首次建槽前已准备，随后到达的空 token 完整回执仍可按同 peer、精确 SHA/大小和 offered 事实核对。空 token 不适用于槽确认，不生成或更换已有 token。

## 覆盖前缀与原文前缀

新的账本不修改旧 `outgoing/<peer>.json` 连续原文回执，也不将旧前缀自动迁成 visibility 回执。新协商需要依据接收方实际保存状态，逐位置恢复相应确认。旧回执和原件继续保留。

covered 前缀只越过具有槽确认或原文确认的位置；original 前缀只越过具有真实原文确认的位置。原文回执可以在较早槽仍 held 时独立保存，因此后续公开原文不会受发送侧连续原文游标限制。

静态推演：槽 1 被确认、原文 2 被确认时，覆盖可到 2，原文确认前缀仍在 0；后来原文 1 合法补发并获得完整回执，原文前缀再核对到 2。不能仅凭槽确认就将 original 前缀报成 2。这些推演来自代码分支回顾，没有运行场景验证。

较晚的覆盖确认不能越过未经确认的位置；高于下一覆盖位置的 ACK 返回范围错误。准备或 offered 可以提前登记，但没有确认的节点不能推进任何回执前缀。与当前位置无关的 peer、source、SHA、大小或 token 不会覆盖已有绑定。

## 中断恢复与有界核对

每个位置的确认节点先通过私有原子写入保存，head 后保存。节点是回执事实，head 是保守检查点；节点已保存但 head 失败时，下一次读取只从连续的已确认节点恢复，不从文件存在、token 或 offered 状态猜测 ACK。

同一个公开调用的核对共享最多十六个节点、约 2 MiB 原文软预算，确认前后的两次核对不会各用一个完整预算。边界和目标记录校验仍可能额外读取原文，不声称该软预算是整次调用的实际 I/O 上限或设备耗时。

大段历史在早期槽填齐后可能需要多批核对。返回 `checking=true` 表示预算内尚未证明原文回执边界，不能把暂未核对的部分说成对端丢失。新确认的相邻覆盖节点已独立校验和持久保存，可以立即推进覆盖，不等待原文历史全部核对结束。后续 progress 继续推进保守原文前缀。

重复确认和读取前缀会重写已经核对的小型节点/检查点，通过现有私有写入的 fsync、rename 和 backend barrier 完成真实耐久边界，不因 rename 暂时可见就直接报告成功。目录创建同步父目录；源身份初始化也检查新增目录，不能在留下旧发送记录时生成一个新 source。

缺失检查点且目录非空、已覆盖节点缺失、错误 JSON/布尔/计数、原文损坏或已确认标记矛盾均失败并保留数据。没有静默覆盖旧节点、擦除原件、重置为完整同步或按“最大序号”跳过缺口。
