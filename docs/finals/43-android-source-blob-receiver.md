# Android 源音频归档接收与独立回执

日期：2026-10-24。任务 05 的 Vela→Android blob 接收子阶段。仅修改源码和文档并做静态回顾；没有测试、构建、编译/语法检查、格式化程序、模拟器或设备操作。本阶段接通 42 阶段 Vela 服务的 Android 调用者，不代表完整双向 blob、全部事件复制或运行验收完成。

## 仓库及数据库

后续本机 MP4 原始字节描述符、后台归档与历史文件观察见 [44 阶段](44-phone-original-audio.md)。该阶段将纯归档与媒体可解码性分离：归档校验原文绑定、完整哈希及大小，不再以 RIFF/WAVE magic 拒绝复制原件；ASR/播放器仍负责实际格式检查。下文保留本 WAV 接收阶段的实现边界。

重新读取独立源仓库的 BufferRepository，仍为数据库版本 19，没有现行源事件或 blob 交付模型；继续修改参赛快照的应用集成，未覆盖独立仓库。

新增 `data/local/BufferSourceBlobs.kt` 和 `data/device/VelaSourceBlobPull.kt`。数据库由 25 升至 26，新建 `source_event_blob_receivers`，保存 event ID、owner peer、source/sequence、原文 SHA、音频 SHA、大小、交付状态、重试时间和固定错误状态。原 source ID、原文、序号、旧回执和卡片不重建。升级只重设派生历史扫描游标，由已有 worker 分批发现旧描述符。

来源历史 worker 只从已经核对原文/指纹及提交游标的远端事实创建任务。识别 schema 1 的 CaptureCreated/LegacyAudioSnapshot，严格检查 WAV 描述符的字段、类型、安全整数、mode、大小和哈希。最大音频为 2 MiB，与 Vela 现有配置允许的最高值对应；实际能从设备读取的大小仍受其当前配置限制。未知描述符保存 unsupported 状态，不执行或补猜字段。

源事件导入与历史 work 入队已有同一事务保证，因此即使在 blob 任务生成前退出，重启仍能接续；生成任务本身不再追加一条 source event。每次选取、保存、确认和重试都重新核对原文、owner pin、提交进度以及任务全部身份字段。任务索引不一致会隔离为冲突，不用当前提示覆盖旧绑定；每轮最多检查八个坏候选，避免一个坏项永久堵住其后的正常任务。

## 分片接收与权限

控制器在已认证 Enrollment Active 状态创建，绑定当前 peer/generation。它与卡片、源 pull、源 push、父项定位五项轮流获得发送优先机会；原配置、既有回执、runtime 和心跳保留其原先优先级。文件和 SQL 操作在现有应用 worker，不在 BLE 回调或 UI 线程执行。

调用 42 阶段的 blob.get/part/accepted/receipt，严格核对字段集合、UTF-8、协议版本、每个逻辑请求的新 nonce、两种哈希、source/sequence、offset、total 和协商帧预算。每片最多 3072 字节，Base64 必须规范；重复片必须逐字节一致，未来偏移或变更描述符不能拼进原音频。

最多组装一个 2 MiB 音频；还有原文解析、文件校验及编码对象等临时分配，不能据此声称整个进程只用 2 MiB。RAM 前缀没有持久回执；断连/退出清理缓冲，缺少完整归档时重新从 offset 0 拉取，而非谎报断点已落盘。下载任务本身持久保存，完整文件可直接接续确认。

每次发送及处理回复复核当前通道授权；Vela 每片沿用原事件分享策略。旧固件无响应、unsupported、withheld、来源冲突和存储错误保留任务并退避，不跳过后宣称交付完成。失效通道的旧 nonce 回复不能推进新连接。

## 私有归档与提交顺序

完整音频必须通过声明大小、整份 SHA-256 及 RIFF/WAVE 标记检查。归档路径只由固定私有根 `files/source-blobs/`、已验证的 64 位哈希和固定 WAV 后缀生成；不采用远端路径。

目录模式 0700，文件模式 0600。读取使用 O_NOFOLLOW，检查同一 fd 的常规文件类型、大小与私有权限，按预期大小有界读取并检查 EOF；不把任意存在的同名文件视为有效。临时文件沿用 RecoveryFiles 的数据 fsync 和 rename，随后核对最终文件、同步权限元数据和父目录。归档根目录的父目录也同步，不能只保证数据文件而漏掉新建目录入口。

顺序为完整验证 → 私有临时文件/原子保存 → 最终文件和目录持久化 → SQLite stored → accepted → Vela 持久 receipt → 再次核对本机归档 → SQLite confirmed。

| 阶段 | 可证明的范围 |
| --- | --- |
| pending | 描述符已登记，完整音频未确认归档 |
| stored | 手机已核对并持久保存音频，设备回执尚未在手机确认 |
| confirmed | 手机已收到匹配的设备持久回执，并重新核对本机归档 |
| unsupported / conflict | 描述符不支持或原文/索引绑定冲突，保留原文并停止该项自动交付 |

文件先提交、DB 状态后提交。文件完成而 DB 失败时，下次重新读取并核对同一哈希文件后补记；不会先发送 accepted。Vela 已记录而手机最终 DB 更新失败时，从磁盘重新核对并幂等确认，不将其解释为设备从未保存回执。

## 复用、重连与损坏恢复

- 旧 raw 输入已经保存该 capture 的 `.bin` 时，只有 capture 的 trusted source 与当前 peer 相同、路径位于本机 captures 根、完整内容与原事件哈希/大小一致，才复制到新的源归档。不会调用旧输入导入器、重新创建卡片或调度转写/模型。
- 每次 Active 先处理到期积压，再按稳定 event ID 逐项重查已确认归档并重新确认设备回执；由此发现缺失文件，并可补记设备端丢失的交付元数据。一次只处理一个任务，不保留整份历史在 RAM。
- 同名归档损坏时，不确认交付。只有取得整份且匹配原始描述符的替代音频后，才把坏文件移到私有唯一隔离名并同步目录，再恢复规范哈希路径。损坏副本和旧原文不自动删除；磁盘不足或文件系统错误仍明确失败。
- 完整 RAM 音频遇到本机保存失败会保留并短时重试；多次失败后持久退避并让其他任务继续。DB 不可用时不会只推进 RAM 游标。
- 请求/响应超时、远端存储失败与分享受限以固定状态持久退避；重试时间异常超出最大窗口时允许重新检查，避免墙钟回退造成长期挂起。待处理和已确认核对分别建立索引，空闲时不重新哈希全部历史。

归档写入/核对使用独立文件锁，锁内不回调 repository 或获取数据库锁；metadata 方法遵循既有 repository monitor。DB 和文件不假装是一个跨资源事务，而是以可重试文件提交及派生任务衔接。断连只清理 RAM，已保存数据和 native 归档继续保留。

## 详情状态与手动核对

来源历史在事件因果状态之外，单列音频待归档、本机已存待回执、双方已记录、来源未开放共享、旧设备不支持、校验失败和来源冲突。事件 linked 或源原文回执不再被当作音频完成；confirmed 描述已经记录的交付事实，不是无限期硬件完好承诺。

“重新核对音频”只将可处理任务重新排队。控制器仍需当前有效通道、原文证明及完整文件校验；该按钮不增加分享权限，不修改未知描述符或冲突绑定。离线时请求保留，连接恢复后接续。详情轮询只读小型状态，不反复加载整份音频。
