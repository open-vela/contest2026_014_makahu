## 未满足的要求

### 1. 缺少可审核、可启用的能力建议对象（P1）

当前分类结果主要是 segments、关联和展示结构；周回顾输出是总结及建议。它们没有将真实历史依据、触发条件、读取范围、动作边界和撤销方式绑定到一个有稳定 ID/版本的能力提议。

因此，用户无法审核“为何建议、允许读什么、何时运行、会产生哪些动作”这一完整草图。不能将一条“喝水建议”或手动设置的专注提醒视为已经实现文档中的“长专注恢复模块”生长机制。

### 2. 缺少能力授权、撤销与执行之间的连接（P1）

现有系统权限和单次动作确认有实际作用，应继续保留。但操作系统允许读日历，不等于用户已启用某个基于历史触发的生活模块；用户批准一个模块，也不能代替执行器所需的本机系统权限和单次确认。

当前没有将“已批准的具体能力版本”绑定到持久任务、执行前授权复核和撤销后取消的通用路径。由于能力生命周期本身未接入，不能评价其撤销已安全闭环，也不能凭系统权限弹窗判定满足本项。

### 3. 外置 Skill 资源仍是归档材料（计划中的未完成项）

`data/agent/README.md` 明确写明仅归档、没有加载器、未加入构建产物；`catalog.json` 顶层 enabled=false、invocation=disabled，四项资源也分别关闭。Android 分类提示词与 Vela 的规则/工具定义仍由代码直接提供。当前 Gradle/CMake 的相关接入也没有将该目录作为运行资源加载。

这是资源目录声明的现状，不能将 disabled 本身报告成回归故障。产品文档要求的是用户控制的 Capability；任务清单另选了外置 Skill 加载作为实现步骤。二者必须区分：即使加载 Prompt 成功，也不能自动授予产品权限；反过来，硬编码能力授权也不等于已完成清单约定的外置资源加载。

## 按依赖关系拆分的后续步骤

1. 定义受限的能力草图结构：ID、版本、真实来源事件/卡片、适用期限、触发条件、读取范围、动作白名单、输出、确认和撤销策略。解释文本不能替代机器可校验的边界。
2. 添加建议存储和事件：提出、拒绝、过期、批准、停用、撤销及版本变化。建议与授权分开保存，重复导入和重复点击不能产生多个有效授权。
3. 从已授权历史生成草图并做结构及来源校验；只允许引用可核实的记录，不允许建议生成过程写外部系统或执行生成代码。
4. 增加草图详情、来源查看、显式启用、关闭及撤销入口。批准针对具体版本；模块读取范围、触发规则或行为扩大后重新取得确认。
5. 将已启用版本绑定到现有受限执行器。任务保存授权修订和幂等身份，入队与执行前都核对当前许可；历史同步不直接触发外部动作。
6. 撤销时取消未执行任务并使旧租约失效；正在运行的可取消读取立即取消，迟到结果提交前再次复核。已完成外部动作的撤回使用对应执行器能力及用户确认，不能把停用模块表述为已撤销所有历史副作用。
7. 按清单实现受限资源加载：校验目录、版本、大小、格式、工具契约和输出结构，绑定已批准能力版本；失败明确反馈。加载资源不提供任意脚本、shell 或额外工具权限。
8. 回顾默认未启用、重复批准、建议过期、历史更新、系统权限撤销、应用关闭模块、重启、离线与跨设备任务等路径，再勾选整个大项。
