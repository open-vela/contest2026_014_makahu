# 手机原始音频描述符与历史文件观察

日期：2026-10-24。任务 05 的手机本机音频准备子阶段。只修改源码和文档并做静态回顾，未运行测试、构建、编译/语法检查、格式化程序、配置生成或设备操作。Android→Vela 的 blob 发送/接收网络链路仍未实现，不能把本机归档 ready 当作对端已交付。

## 格式与原始字节

读取了当前 MainActivity、RecordingFinalizer、ASR、捕获/恢复路径及独立源仓库对应文件。手机实际使用 MediaRecorder 的 MPEG_4/AAC，原格式包含采样率等参数；不能转成 WAV 后把转换结果当成原件。继续修改参赛快照，未覆盖独立 Fabric 源仓库。

blob 描述符继续使用 sha256、bytes、content_type、created_at、duration_ms、mode 六字段。保留原始 MP4 字节；MIME 规范化为 audio/mp4、audio/wav 或 application/octet-stream，原 audio_format 字符串仍留在 CaptureCreated 中。哈希路径分别使用固定 mp4/wav/blob 后缀，不从远端格式字符串构造任意路径。

修正 43 阶段的归档验证边界：**归档验证大小和完整哈希，不要求原始音频一定能够解码。** 去掉归档层 RIFF/WAVE magic 门禁，避免把已存在但不可解码的原件排除在复制之外。实际 ASR 的容器/信号检查及旧 raw 输入协议的 WAV 检查保持其原用途，没有把归档数据自动送入解码器或执行器。

数据库由 26 升至 27，为已有 blob 任务增加 content_type，旧 WAV 任务默认值保持匹配；增加 `source_event_local_audio` 与稳定 capture ID 扫描游标。升级重新安排派生历史扫描。此前因描述符不支持而停留 unsupported 的任务，只有原文 SHA、owner 和完整身份仍一致且新解析器支持时，才转入 pending；不改写原事件或已确认回执。

## 本机来源与捕获提交

新增显式 localOriginal 参数，默认 false。录音 UI 的保存和重试备份明确传 true；LAN BufferWire 和 Fabric 设备输入没有从请求读取这个标记，仍按非本机原件处理。true 还必须符合本机来源身份；不能只看请求方传来的 android 名称就把设备导入音频转成本机原件。

新录音在既有私有 `.bin` 原件写入、目录同步后，将完整字节 SHA 和描述符加入首次 CaptureCreated，并在同一事实事务登记本机归档工作。输入先复制成有界稳定快照，避免调用者修改 ByteArray 导致文件与描述符不一致；快照使用后清理。额外哈希归档和旧文件处理由后台 worker 完成，没有在录音最终保存入口增加第二份完整归档写入。

录音启动先以 O_EXCL/O_NOFOLLOW、0600 创建本次缓存文件，再交给 MediaRecorder；启动失败只清理本次确实创建的文件。恢复元数据新增 record_sha256/record_bytes，绑定已经保存的来源、时间、格式和本机标记。旧元数据缺少校验和时不能通过外部调用继承本机原件标记或旧的本机上下文采集请求；可信的本机/恢复入口仍保留旧策略快照。

已有 capture ID 的重试必须核对来源、时间、mode、格式、时长与原始文件内容；有已提交 portable SHA 时还核对该证明。原件缺失但有匹配原文校验和的重试可以补存相同字节；没有历史校验和时不凭调用者数据猜测缺失原件。不会因已有卡片就直接返回成功，或用新的录音覆盖旧文件。

恢复继续使用原文件/元数据，核对可用校验和，拒绝不一致组件；重复 preserve 保留原策略及来源元数据，不因当前设置或一次新的调用改写它们。元数据和音频先后失败均保留已提交部分，文件与目录同步失败不被当作成功保存。

## 后台归档与旧 blob_ref

新增 `BufferLocalAudio`，复用独立来源历史 worker。每批最多处理四个 capture、每份原文件最多现有手机上限 512 KiB；稳定游标沿现有 source capture 索引逐 ID 查找，不依赖派生 captures 行完整存在，不将音频文件加载成整份历史集合。新音频另有事实事务中的直接入队，不因其 ID 小于旧扫描游标而遗漏。条数/字节有界不等于已验证实际耗时。

新 CaptureCreated 已有描述符时，后台核对 `.bin` 与原文 SHA，保存私有哈希归档；若完整哈希归档已经在 DB 状态提交前保存，则从该档案恢复 ready，不依赖仍有派生捕获行或旧绝对路径。检测到原件与已知校验和不一致时不发布另一个 checksum 来掩盖损坏。后台与文件 helper 的锁内不执行模型或业务副作用。

旧 CaptureCreated/blob_ref/envelope 不改写。只有本机来源标记，或旧代码中由本机 UI 写入的 context_local 与来源证据能核实时，才读取固定 captures 根下匹配的文件。不能把来源名称、当前权限、导入者 actor 或文件在本机存在本身当作本机捕获证明。证据不足的记录保持 unverified，保留文件和旧事实，不生成可自动转发的描述符。

旧文件成功归档后，追加当前时刻的 CaptureBlobDescribed，标记 observation=legacy_file_now，并引用原 CaptureCreated 的 event ID 与精确 envelope SHA。该引用同时进入父事件列表，和当前 capture 的因果父项去重。这说明“现在核对到这份文件”，不声称原始捕获当年已经记录同一 checksum，也不补采过去的位置或日程。

档案指针、观察事件、源序号和工作完成状态同事务提交。文件先保存而事务失败时保留归档，重试仍核对既有文件；已发布描述符的重新核对只恢复相同 SHA，不更换原文或重复追加观察。旧 schema 本身不受支持、源证据冲突或文件暂不可读时分别保留未核实/冲突/有界退避状态，不把它当作无音频。

## 用户状态与网络边界

来源历史增加本机待归档、已归档但未记录对端交付、原件暂不可读、来源未核实和需核对状态，并提供本机重新核对入口。重新核对不授予新来源或共享权限；未核实记录不能靠该按钮直接变成本机原件。所有详情状态只读小型索引，归档读写仍在后台进行。

源事件通道可以携带新的可移植元数据，但本机 ready 仍只表示文件准备完成；原 source event 回执也不表示 MP4 已传给 Vela。本阶段未加入反向二进制发送、Vela 远端 blob 持久接收或手机发送侧 blob 回执。这些必须继续与当前分享策略、原文/owner 绑定及独立提交证明衔接。
